## Problem

From GitHub GC#32: WorkItems pile up in the wrong status — they don't fully advance to `done`. Root cause (grounded in `core/view/workitem_index.py::compute_phase`): an item only derives to `done` when its linked spec is `implemented` or `archived`, but nothing advances the spec there after a PR merges — so finished work sits in in_flight/review forever. The issue also asks for manual escape hatches: set an item's status by hand, and swipe-archive specs to clear clutter.

## User story

As the operator, my finished work items actually reach `done` on their own, and when something is stuck I can "Mark done" / "Reopen" it from its card, and swipe old specs to archive — so the board reflects reality instead of accumulating stale items.

## Approach

Cross-repo. Decisions captured from the brainstorm: full issue scope; fix the bug at BOTH the close step and the derivation; manual set-status = quick actions (Mark done / Reopen), not a full picker; swipe-archive lives on the spec inbox.

**mothership**
1. **close → implemented** — `mship close` (post-merge cleanup) advances the task's linked spec `dispatched → implemented`, so `compute_phase` returns `done`. Idempotent; no-op when there's no linked spec.
2. **Derivation backstop** — harden `compute_phase` so a WorkItem whose work has landed (all linked tasks in a finished/merged state — see q3) derives to `done` even if the spec status lags. This covers unattended runs where the operator merged the PR without `close` being run.
3. **Serve endpoints** (both new): set/clear a WorkItem's `phase_override` (for Mark done / Reopen), and archive a spec (→ `archived`). Reuse the existing item/spec locks + patterns in `serve.py`.

**ground-control**
4. **Item quick actions** — on the WorkItem card (farm/cockpit), "Mark done" (POST phase_override=done) and "Reopen" (clear override), with optimistic update + revert-on-failure (mirror the FarmViewModel unattended-toggle pattern).
5. **Swipe-to-archive specs** — in the spec inbox, swipe a spec to archive it (POST archive), removing it from the active list.

Testing: mothership unit tests for close→implemented, the derivation backstop (landed → done; in-progress → NOT done), and the two endpoints; GC JVM unit tests for the VM actions + `mship build` (assembleDebug). This spec is the first intended job for the unattended runner (a cloud Claude routine via `mship bootstrap` → `mship item run-next`), so the acceptance criteria are written to be verifiable by an autonomous run.
