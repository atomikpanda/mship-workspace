## Problem

The self-hosted sish relay runs with `--idle-connection=false` (docker/relay/docker-compose.yml:32), carried unexamined from the original relay plan (docs/plans/2026-06-16-low-friction-phone-connection.md:88, shipped in 5cc46b9 / #187) with no recorded rationale. The flag does not mean "do not disconnect idle tunnels" — in sish it is the only thing that decides whether `CopyBoth` wraps a proxied stream in `IdleTimeoutConn`, which re-arms a `SetDeadline` on every read and write (utils/conn.go:229). With it false, every proxied stream between an inbound HTTP connection and its SSH channel runs with no deadline in either direction. A tunnel peer that vanishes without a FIN — cell handoff, NAT eviction, laptop suspend, i.e. the normal life of a phone tunnel — leaves that copy blocked forever, its channel open, and its subdomain route still registered in sish.

The observed consequence is an unbounded goroutine leak. A goroutine dump from a relay up 28 days showed 137 goroutines, 60 of them parked in `chan send`, topped by `handleRemoteForward.func7.1` (61) into `SSHConnection.SendMessage` (59), against a goroutine ID of 14,791,699. Each inbound request for a stale route fails `OpenChannel("forwarded-tcpip")` and then calls `sshConn.SendMessage(err.Error(), true)` (sshmuxer/requests.go:439). `Messages` is unbuffered (`make(chan string)`, sshmuxer/sshmuxer.go:282) and the blocking form of `SendMessage` is a naked `s.Messages <- message` with no select, no `Close` case and no timeout (utils/conn.go:46-50), so every one of those sends parks forever. Nothing drains them because the only consumers are `checkSession`'s discard loop (sshmuxer/handle.go:57-65) and `handleSession`'s writer (sshmuxer/channels.go:81-90), and the latter writes into the dead session channel with no idle deadline and wedges there.

This is very likely the same root cause as the recurring orphaned-tunnel / duplicated-subdomain symptom the operator has hit before: routes whose cleanup never runs because the connection is never torn down.

## User story

As the operator of the mship relay, I want a dead phone tunnel to be reaped promptly, so that stale subdomain routes and leaked goroutines do not accumulate until the relay degrades or has to be restarted.

## Approach

Restore sish's default reaping and tune the timeout for phone tunnels rather than for sish's 5s default.

In `docker/relay/docker-compose.yml`, drop `--idle-connection=false` (taking sish's `true` default) and add `--idle-connection-timeout=120s` in its place, with a comment recording why the value is what it is. 120s is chosen against the client we already ship: `build_tunnel_argv` passes `ServerAliveInterval=30` and `ServerAliveCountMax=3` (src/mship/core/relay/tunnel.py:73-74), so a live-but-quiet tunnel refreshes the deadline every 30s and never trips a 120s idle timer, while a genuinely dead peer is reaped within ~2 minutes instead of never. The client keepalive is what makes it safe to re-enable the reaper without reintroducing the "idle tunnels get killed" failure this flag was presumably meant to avoid.

Because the relay config lives in the repo but the running relay does not redeploy on merge, the change is not done until the live relay is recreated with the new flags and verified — the same deploy-gap that bites `mship serve`. The spec therefore covers the deploy and the post-deploy verification, not just the file edit.

Separately, file an upstream sish issue for the unbuffered-`Messages` blocking send. The idle deadline makes the wedge rare, not impossible: as long as `SendMessage(_, true)` can park forever on an unbuffered channel with no `Close` case, any stalled consumer reproduces the pileup. That is upstream's to fix; we only stop feeding it.

## Evidence

The diagnosis rests on a goroutine dump from a relay with 28 days of uptime and on sish's source at `main`:

- 137 goroutines total; 60 in `chan send`; top frames `handleRemoteForward.func7.1` (61) -> `SSHConnection.SendMessage` (59). Goroutine ID 14,791,699 indicates heavy churn over the uptime.
- The single `running` goroutine was the keepalive (`handleConn.func4` -> `mux.SendRequest` -> `selectnbrecv`) spinning against the same dead mux.
- `utils/conn.go:46-50` — blocking `SendMessage` is an unguarded send.
- `sshmuxer/sshmuxer.go:282` — `Messages: make(chan string)`, unbuffered.
- `sshmuxer/requests.go:439` — the blocking send on the `OpenChannel` failure path.
- `utils/conn.go:229` — `--idle-connection` is the sole gate on `IdleTimeoutConn` in `CopyBoth`.
- sish flag defaults (docs.ssi.sh/cli): `--idle-connection` true, `--idle-connection-timeout` 5s, `--ping-client` true, `--ping-client-interval` 5s, `--ping-client-timeout` 5s.

## Testing

There is no unit test for a docker-compose flag, and the repo has none for the relay compose file today; asserting on a YAML literal would test the file against itself. Verification is therefore operational and belongs in the acceptance criteria: confirm the flags on the running container, then exercise the dead-tunnel path end to end (establish, fetch, kill uncleanly, watch the goroutine count settle). Capture the before/after goroutine counts as evidence on the relevant acceptance criterion.
